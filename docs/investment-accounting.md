# 投资记账

总览盈亏卡片左上角复用本页投资趋势的下拉组件切换「盈亏日历」和「盈亏月历」，菜单向左对齐，使用相同的文字、圆角浮层、选中底色及勾选样式，本机记住所选视图。日历按月导航，月历按年显示 12 个月，选中月份可查看月度明细并进入对应日历。月度与年度金额直接汇总相同的人民币日盈亏，当前统计截至今天并包含暂估；建账前和未来月份显示「—」。统计范围内缺少任一天完整估值时，不以零补齐，也不把部分已知金额当作完整月度／年度盈亏，显示缺失天数及已知日期的小计。整年日盈亏在后台一次性读取，月份／日期选择复用结果，账本版本或年份改变时重新计算；切换视图不额外请求行情。

## 总览走势

总览首个汇总卡片内的「账户当日盈亏」默认折叠，展开仅显示当日盈亏金额与当日盈亏率，沿用账户币种；排序按当日汇率折合人民币的有符号盈亏金额从高到低，已知金额在前，同额及无法折算时保留账户管理顺序。比例为当日盈亏除以当前资产减当日盈亏（即昨日资产加当日净流入），分母非正或缺少估值时显示「—」，资金转入不作为收益。账户归档显示偏好与原列表一致，点击行进入对应账户。数据在账本汇总时一次性准备，独立于投资趋势，不新增行情请求或修改账本。

总览投资趋势下方的「账户资产与盈亏」合并当前资产占比与账户历史盈亏。左侧上下排列资产和盈亏两个圆环，右侧显示全部可见账户的人民币资产金额、资产占比、历史盈亏金额及历史盈亏率（累计盈亏除以净投入，非正分母显示「—」），保留右上角当前统计日期。轻量「盈利／亏损」开关只切换盈亏圆环，盈利按正收益归一化、亏损按负收益绝对值归一化，零盈亏不占面积；资产圆环、明细内容及顺序不受切换影响。两图和右侧账户使用相同颜色，点击账户同时高亮其存在的扇区，再次点击取消；无对应扇区时不淡化整图。缺少估值或汇率时显示「—」并提示对应图估值不完整，不把缺失值当零，也不绘制误导性的完整占比。账户归档显示沿用设置。无障碍大字号下上下排布图与明细，避免文字裁切。只使用当前已准备的账户估值，不改变保险显示偏好范围、不修改数据库或触发行情请求。

账户页在汇总下分为「账户明细」「图表分析」：前者保留现金管理和持仓操作，后者与总览共用「投资总额」「盈亏曲线」「盈亏率曲线」。图表使用与资产趋势一致的面积、坐标和标签样式；时间为自定义下拉菜单：今年、近一月、近三月、近半年、近一年、近两年、近五年。标的页保留原有价格、持仓和盈亏图内容及交易交互，仅统一图表样式与时间菜单。

历史金额使用已有日终快照，当天使用最新可用估值并标注暂估。总览按人民币汇总，账户页按账户币种展示。盈亏曲线为累计盈亏，切换范围不归零。账户图表下显示各标的及现金在区间内的数据。独立饼图使用当前最新可用估值展示账户或持仓构成；盈亏图内的矩形热力图按账户或标的的区间盈亏分块，面积为盈亏金额绝对值，盈利绿色、亏损红色，零盈亏不占面积。资产占比单独放在主图下方的独立卡片中，右上角保留当前统计日期；与投资趋势解耦，不受趋势时间范围、选中日期或指标切换影响。总览按当前账户总资产折算人民币，账户页按当前持仓估值及现金展示，仅随账本或最新估值更新。点击右侧图例中的账户或标的，高亮对应扇区并淡化其他扇区，再次点击取消；选中项不再有正值资产时清除选择。热力图仍与主图处于同一分组。

盈亏率曲线按每日估值和实际资金进出连乘，区间起点归零，非年化；资金转入、转出不直接当作收益。分母为零、资金记录或估值缺失时不补零，不在缺失后擅自重设起点。累计盈亏率明细仍使用累计盈亏除以净投入。仅盈亏率提供指数比较，切换入口位于图表下方，默认标普500，可切换沪深300。基准接入东方财富真实指数日线，校验市场和代码，剔除未收盘数据，美股收盘对齐北京时间日期；按本币价格计算，不含分红及汇率。两条曲线使用相同的起点，休市日沿用已发布收盘价，缺少起点行情时明确提示无法比较。指数查询不写入记账账户、标的或交易。

## 助手选择与重试

记账助手的最新完整回复中，明确要求用户选择的编号或候选列表可直接点按；点击发送该选项的完整含义及条件，后续仍须在记账预览中确认写入。发送后旧选项停用，普通说明列表保持文本展示。

模型请求失败后，在对应用户消息泡泡左侧显示重试图标，包含 HTTP 400、网络中断及响应不完整等失败。手动重试沿用当前问题、图片及已保存的查询结果，不重复添加用户消息，也不自动确认或再次提交账本写入。正在请求或提交期间禁用重复操作。

## 理财余额与报价规则

股票、ETF、基金、期货、期权及加密货币现货仅使用自动行情，不提供手动报价；界面、助手操作及新增报价写入均遵守此规则。保险保留按日期更新保单现金价值。

理财产品按实际金额与余额记账，不使用份数或单位净值。申购填写申购金额和变动后余额；赎回填写实际到账金额和赎回后余额；实收收益填写到账金额和到账后产品余额。也可通过「更新理财余额」单独记录当前余额，差额计入浮动盈亏，不产生现金收支。全部赎回后余额为零，已实现收益保留；行情查询和估值不依赖理财产品报价。没有存量理财数据，本次不提供旧份额／净值记录迁移。

## 增量保存与外部行情

普通账本保存只提交新增、修改、删除的记录，仍先由服务端确认，再更新本机。账户与交易修改沿用账本 generation 防止并发覆盖；行情单独按标的和日期更新，不推进账本 generation。外部系统可使用单独授权的第三方应用 AK/SK 查询更新需求并批量写入，具体协议见[外部行情更新](market-updates.md)。行情变化继续使本机估值缓存和受影响的日终快照失效，报告功能不变。

## 版本查询

iOS 设置的「版本信息」显示服务端版本、投资数据库实际版本、服务端目标版本及匹配状态，进入页面、返回前台和手动刷新时重新查询。数据库查询需已有 Console 登录会话；未登录或查询失败时显示未能获取，不推断升级完成。

`GET /api/v1/version` 提供公开的服务端及最低客户端版本。`GET /api/v1/investment/version` 使用 Console 的 DPoP 认证，只返回 `version`（实际读取 SQLite `PRAGMA user_version`）和 `expectedVersion`（当前服务端要求），不返回表结构或账本内容。接口只读，查询不会执行迁移。当前服务端为 0.9.1，最低 iOS 为 0.9.0、最低 Agent 为 1.5.10；iOS 和 Agent 最低要求服务端 0.9.0。

## 保险账户

设置提供「保险盈亏口径」，默认「按现金价值」，可切换为「按已交保费」。仅总览顶部卡片的「历史总盈亏」采用该显示偏好：在保保单用当前保单已交保费替代现金价值，部分提取保留为实际现金收益，已退保保单保留实际盈亏，外币按同一当前汇率汇总。总资产、当日盈亏、账户与保单详情、走势图、日历和历史快照继续使用原口径。偏好仅保存到本机，不写入账本，不触发快照重算或网络请求。

人民币和港币均可建立保险账户，保费、现金价值及退保到账金额使用账户币种；同一账户只接受同币种保单。首次录入及续缴累加保费成本，每份保单保持一个持仓；现金价值由用户按估值日期手动更新，支持零值。

保费实际缴纳记录按同一账户、同一保单的交易顺序显示「首期保费」和「续期保费」；期初资产记录仍显示「首次录入」。现金流水、交易明细与助手预览采用相同命名。账本仅记录日期，同日现金转入、划入先参与余额校验，其他交易保留原顺序；后来补记的同日资金可以支付该日保费，后续日期的资金不能支付更早的保费。修改保费替换原流水，只扣除差额，不自动新增资金。

保单详情支持「部分提取」。提取金额进入同一保险账户的现金余额，不属于账户外部转入，也不结束保单。提取后现金价值选填；填写时采用实际值，留空时按截至该日最近已知现金价值扣减提取金额，缺少估值或扣减结果为负时按零估值，并在数据检验中提醒。多笔同日提取按交易顺序计算，后续日期手动现金价值覆盖此前估值；提取当日以交易记录中的实际值或扣减结果为准，可在该笔交易中修改。

累计盈亏为剩余现金价值加累计提取、退保回款减累计保费，提取回款不重复计入账户收益。现金价值为零仍保留有效保单，退保才关闭持仓；退保后保留历史盈亏。部分提取记录沿用点击展开、小字修改、二级页面右上角保存和删除确认，编辑或删除后重新回放现金、估值及相关快照。助手使用 `insurance_withdrawal`，`amount` 为必填提取金额，`settled_amount` 为选填的提取后现金价值；服务端无需数据库结构升级。

资产总额计入保单现金价值和账户剩余现金，不将累计保费再次计为资产。未录入截至估值日可用的现金价值时按零估值，不以保费替代，也不使用未来的现金价值倒填历史。当前资产、盈亏曲线、历史快照采用相同规则；保费成本保留，因此未录入价值时可能显示负盈亏。汇总人民币资产时，人民币保单直接计入，港币保单按对应汇率折算。盈亏为现金价值减累计保费并加已实现收益；退保后保留最终盈亏。

## 数据检验

### 行情请求调度与补数范围

行情请求按渠道分别限制并发，Twelve Data、Tushare、东方财富、Binance 和 ECB 各自最多同时发送3个请求；同渠道的不同接口、子域名及凭据共用这3个名额，不同渠道互不占用名额，完全相同的在途请求仍共享结果。收到 HTTP 429 或响应中的业务错误码 429 后，该凭据全部接口的新请求统一暂停完整60秒，已经发出的请求可以结束；再次收到429则重新暂停60秒。Twelve Data 未获得套餐信息前按每60秒8次保守调度，之后从响应额度头或连接测试返回的套餐额度更新预算。等待不会计入调用次数，页面任务可以取消；取消共享请求的某个消费者不影响其他消费者，全部消费者取消后停止请求。额度与冷却按凭据分别计算，同渠道的并发名额仍共用。

相同请求并发时共用一次网络查询；附近历史缺口合并为区间请求，每段最多365个自然日，避免将周末或节假日逐段当作补数请求。成功查询的完整区间（包括明确无行情的区间）保留覆盖记录；失败不标记完成，未结束的查询日次日仍需复查。不改变既有缓存格式或自动改写历史数据。

新增关注仅查询近14天报价，校验成功后保存查询覆盖；关注与已有相同标的持仓复用缓存。普通自动刷新按每个标的自身最早流水决定历史起点，并保留最近14天用于获取最新报价，不再套用全账本最早日期或至少375天的范围。价格走势图仍按用户选择的范围按需补数，历史资产快照继续按实际需要补齐。错误详情附带脱敏后的请求标的、日期区间与触发原因。

### 行情接口失败详情

Tushare Pro 与 Twelve Data 在各自设置的调用统计下提供失败详情。每个行情源独立保留最近24小时内最多200条记录，按时间倒序排列；默认展开最近一条，展开其他条目时自动折叠前一条，再次点击可收起全部。记录请求时间、接口名称、HTTP 状态、业务或网络错误码和具体错误信息；HTTP 200 中的业务错误也保留。Tushare 使用请求中的 `api_name` 标记接口，不保存 Token、请求正文或完整请求 URL。错误信息中的凭据先脱敏再落盘，复制仅写入本机剪贴板。

失败列表标题、每条错误标题与展开详情使用独立表单行；点击后在当前标题下插入详情并向下排列，关闭列表重排动画，避免整个长列表作为一个变高的单元格带动上方内容跳动。

统计刷新任务与统计、小时选择、失败列表展开状态由凭据页面持有，不绑定到可回收的图表行。每5秒读取本机统计，重复快照不触发更新；图表滚出屏幕、重新出现或读取失败时保留现有数据与展开状态，不通过清空长列表重新加载来刷新页面。离开配置页时取消任务。

详情保存在独立的本机文件并排除备份；更新前的次数记录无法补回具体原因。记录过期或超过容量时只移除详情，不改变仍在24小时窗口内的调用统计。存储失败保留当前内存记录并显示提示，不阻断行情请求。

### 数值精度（schema 7）

数量输入框下不常驻显示精度说明；点击保存后，数量超出允许精度时才显示错误提示。

美股股票、ETF、基金和加密货币的数量输入统一最多允许 3 位小数，例如 5.711 股或 0.058 BTC；超出精度时提示修改，不自动舍入。录入、买卖、编辑交易、助手操作和加密货币余额调整使用同一规则。定投自动计算份额时按 0.001 单位向下取整；其他市场股票、期货和期权仍要求整数。已有历史数量不改写，旧余额与新目标余额的计算差额保留精确值；数量仍以十进制原值保存，现金、费用和单价继续按各自规则计算。此调整不改变数据库结构。

汇率、交易单价和行情报价（含净值）固定保留最多 4 位小数；交易数量按十进制原值保存，不套用金额舍入，避免 `0.058 BTC` 被改成 `0.06 BTC`；其余投资库数值（包括金额、利率和合约乘数）保留 2 位，只有原值整数部分为 0 且小数点后前两位也为 0 时保留 4 位。负数按绝对值判断，按四舍五入舍入。整数序号、版本及标识不参与舍入。数据库继续使用十进制字符串，舍去多余小数及无意义的尾零，不经过浮点数转换。例如 `461884.884061… → 461884.88`、`0.00123456 → 0.0012`、`1.00123456 → 1.00`、汇率 `7.123456 → 7.1235`；低于四位精度的值可能舍入为零。交易数量在数据管理列表和字段详情也显示原值；其余数值使用相同显示规则，例如 `330000.00`、`123.00`、`0.0012`、`0.0000`，汇率和数据管理中的单价、行情报价始终显示四位。

买入实际支出和卖出实际回款（含费用）使用金额精度，建仓和已有持仓追加买入均提供「自动转入本次所需现金」选项，默认关闭；开启时按成交日期先新增一笔与本次实际支出（含费用，合约按保证金及费用、港股通按清算金额）完全相同的现金转入，再记买入，保留原有现金余额。关闭时仍使用已有现金。转入和买入一并校验、提交或回滚，不改写此前自动补足的历史记录。发送源记录前，用序列化后的数量、价格、费用重放本次涉及的账户，阻止会导致负现金或超卖的写入；读取与展示不因负现金余额而中断，仍显示已有余额及流水；严格余额校验在提交新增、修改和删除时执行。交易表单中的单价最多允许 4 位小数；金额和费用等继续沿用金额精度，受限输入即时提示精度错误，提交时再次校验，不能静默改成另一个值。本次不自动改写历史数量，已经被舍入的原始数量需要核对后通过流水编辑更正。四位单价规则要求服务端 0.8.18 与 iOS 0.8.178 协同更新；iOS 最低服务端版本为 0.8.18，避免旧服务端再次把单价舍入为两位；数据库仍为 schema 7，无数据迁移。

schema 6→7 的临时数值整理、启动调用及迁移专项测试已移除；正常写入的精度处理长期保留。当前仅接受 schema 9，不在启动时执行旧结构迁移或整理旧数值。清理前已通过 Agent 签名只读查询核对线上 schema 7、目标表结构及所有已有数值字段精度。

历史迁移版提交 `68f1e13`（服务端 0.8.2）在同一事务中将 schema 6 的已有数值整理为新精度，再标记 schema 7；无效数值或写入失败整体回滚，不推进版本。受影响账本递增 generation，源数据变化时同时递增 revision，并从最早交易／快照日期标记历史快照失效，由 iOS 重新计算。此段只记录历史行为，当前代码不再执行。

### 数据管理与磁盘缓存（0.8）

投资记账设置的「数据管理」提供「本机」与「服务端」两种视图，按行情、汇率、投资资产日终快照、投资账户日终快照分类。可逐层查看标的、日期和原始字段；本机数据可按全部、类型、标的或单条清理，服务端视图只读。清理本机副本不删除服务端记录和交易。

已确认账本、行情、汇率和日终快照保存在应用支持目录的磁盘文件中，按服务器和登录账号摘要隔离，原子写入、排除系统备份并使用设备文件保护。退出应用后仍保留，读取先使用本机数据；本机范围缺失时查询服务端，仅向行情 API 补取服务端未覆盖的历史区间。查询覆盖范围也落盘，以免把休市日的无报价误当成未查询；当天区间次日重新检查。自动进入、下拉刷新和历史曲线统一复用持久化的行情、汇率与查询覆盖记录；按日期扣除已有数据及成功查询的空区间，只向外部 API 补取本地和服务端都缺失的日期，包含序列中间的缺口。网络失败、鉴权失败或无效响应不记为已查询；尚未发布的当天区间次日允许重新确认。API 新取得的行情与汇率先原子写入本机磁盘，再同步服务端；服务端写入失败保留本机数据并用于估值，下次只重试同步，不重复查询外部 API。账本中的账户和交易等用户源数据仍先由服务端确认，再缓存到本机。历史曲线不创建交易或执行定投。

各投资账户的日终快照分别从该账户最早一笔交易的日期开始，包括现金转入和首次录入；尚未记账的账户不生成账户快照，最早交易仍在未来的账户不提前生成零值快照。总览快照仍从整个账本最早交易日开始，各账户独立回放自己的流水。提前、推迟或删除某账户的最早记录时，重算同步调整该账户的快照范围，其他账户按各自原有记录计算。打开时只检查已保存截止日及受影响日期标记，不扫描、回放全部历史；仅补齐缺少的日终日期或重算已标记的受影响区间。完整检查由「数据检验」手动触发；已有的范围外派生快照通过「重新计算历史快照」清理，生成与写入时持续约束账户范围。记账后真实的零值快照保留，不需要数据库结构迁移。

月度余额、对比及更新记录改为筛选 `investment_daily_snapshots` 中的月末日期，不再冻结或存储第二份月末总额。缺少月末当天的日终快照时保持缺失，可通过重算历史日终快照补齐。

投资库为 schema 9，不再包含 `investment_month_snapshots`。schema 5→6 和 6→7 的临时迁移代码、专项迁移测试和启动调用已清理；schema 7/8→9 的公共行情升级及清理记录见下文。历史迁移版提交 `b8ff7b8` 只删除该派生表并递增账本 generation，保留交易、行情、日终快照及 revision；失败整体回滚。旧 0.7 客户端仍可能提交月末表，因此当时服务端与 iOS 使用 0.8.x；Agent 1.4.7 将最低服务端更新为 0.8.0。

各类资产价格和汇率缺少当天数据时，均沿用该日之前最近一笔有效数据；连续多日缺失时持续沿用，不区分工作日、周末和节假日，也不限制追溯天数。新数据出现后从其生效日切换，沿用不会生成虚假的当日报价记录。日终快照仍排除未定稿的盘中价格和汇率，不使用未来数据倒填历史；美股收盘价仍按下一北京时间日期生效。只有截至该日从未取得可用数据时，才报告缺失；估值、历史盈亏、快照和数据检验采用同一沿用规则。

投资记账设置中的「数据检验」进入二级页面，由按钮手动触发。检验直接读取服务端最新账本，在后台线程检查全部账户（包括归档账户）的交易回放、标的引用、重复标识、划转对应关系、估值、汇率及历史快照；不会写账、补行情或重算快照。结果区分影响计算的问题和提醒，列出账户、标的、原因及全部受影响日期；连续日期合并为区间，不截断问题列表。单个账户流水错误不阻止检查其他账户。保险缺少现金价值作为按零估值提醒，已明确录入零值不提醒。修复或重算后须重新检验。

「数据管理」「数据检验」「重新计算历史快照」「导出账本」「数据备份」合并在同一「数据」分组。历史快照入口进入二级说明页，说明用途、适用情况、日期范围及结果保存方式，点击「开始重新计算」才执行；覆盖记账开始日至北京时间昨天的全部账户，保留原始交易流水，复用已有行情和汇率，仅补查缺失项，缺少的数据仍保持缺失。盈亏日历的记账首日以开始前累计盈亏为零计算，无须前一天的快照；首日之后仍要求前后两天快照完整，真实缺口不以零补齐。资产占比圆环中央留空，金额和比例保留在图例。

账本写入统一在发送请求前校验字段白名单、必填项、主键重复、数值与整数格式、日期、枚举、表间引用、定投周期、源数据与快照分离及快照版本；继续执行金额精度和受影响账户流水余额校验。服务器保留独立校验、权限检查、最新账本版本冲突检测和事务提交。客户端规则通过契约测试与服务端保持一致。

投资记账设置移除独立的「行情与汇率」分组及刷新按钮，保留自动补缺与下拉刷新。「行情接口」分组内首先显示默认折叠的「渠道说明」，按无序列表介绍东方财富、天天基金、Twelve Data、Tushare Pro、Binance 与欧洲央行的数据范围及密钥要求；下方为 Tushare Pro 和 Twelve Data 配置入口。进入各接口的二级配置页，直接编辑密钥，通过右上角勾号保存；未修改时禁用保存，关闭或下滑时保护未保存的修改。连接测试下方显示最近 24 个小时（含当前小时）的本机调用量，横轴为小时、纵轴为次数，每小时用绿色、红色两根并列柱分别表示成功、失败，并显示各自合计；可点选查看每小时次数。每个已完成请求计一次，归入发起小时，包括搜索、行情、汇率和连接测试；网络、HTTP、接口业务错误及无效股票报价计为失败，缓存命中不计入；搜索词变化、关闭页面等导致调用任务取消时，不计入成功或失败，也不新增失败详情。调用任务未取消却收到传输层取消错误时仍保留诊断。Twelve Data 包含 Binance Stock 报价。统计只保存供应商、小时和成功／失败次数到本机磁盘，不保存 Key、URL 或请求内容；重启后复用，过期小时自动淘汰。成功／失败结果从本次新版开始记录，旧版总次数不回填为成功或失败，不代表供应商账单或其他设备用量。读取图表不调用行情接口。

## 行情与标的搜索

投资页面从磁盘恢复时一次读取缓存文件，统一解码账本并补装本机行情；行情刷新也只读取一次磁盘缓存，按行情键建立只读索引，标的、加密现货与汇率共用，不按标的或补数窗口反复解码整个文件。本轮查询成功的区间在内存中记录覆盖，避免重叠窗口重复请求；下一轮刷新重新读取，能够看到其他缓存实例的写入，不使用跨轮次的常驻内存缓存。读取与索引有独立耗时，诊断信息记录各标的的缓存缺口、已有报价数和请求区间数；有本机已保存会话时与服务端会话恢复并行，先显示缓存，再继续远端校验。账户和总览使用按账本版本在后台准备的流水、汇总和持仓顺序，切换账户及打开表单不在视图重绘中重放整本流水。写入前的编码、差异校验与确认后的解码同样在后台执行。

保存持仓时按钮显示加载状态，防止重复提交；已有报价和汇率直接复用，缺失时仅补最新报价与必要汇率，美股使用 `/quote`，东方财富日线及基金净值仅取一条。保存不等待价格走势图，最新报价缓存不冒充历史查询覆盖。服务端确认后先准备账户市值、盈亏及持仓顺序，再关闭编辑页；行情准备失败发生在提交前，保留输入并明确提示，不在已经保存后诱导重复提交。走势图仍在标的详情按需加载。

美股及美股 ETF 的搜索结果只在美国、美元、代码、完整名称和证券子类型一致，且仅有一个明确主市场时，将对应的 IEX 交易场所记录合并为主市场的一项。名称仅忽略大小写和连续空白，不模糊匹配不同股类；主市场冲突、未知市场或仅有 IEX 时保留原结果。不增加目录请求。所选结果保留原始市场及名称用于行情路由，保存校验查询完整未合并目录；已有持仓、关注与资产标识不变，不修改数据库结构。

美股和美股 ETF 使用 Twelve Data，需在投资记账设置中配置 API Key。搜索使用 `api.twelvedata.com/symbol_search`，按资产类型、USD 币种、美国市场及交易所 MIC 筛选；历史行情使用 `/time_series` 的未复权日线收盘价，核对代码、币种及已指定的交易所。Nasdaq 总市场 `XNAS` 使用 `exchange=NASDAQ` 筛选，返回 MIC 仅接受 `XNAS`、`XNMS`、`XNGS`、`XNCM`；明确指定细分市场时仍按 MIC 精确筛选与校验，不因接口错误改查其他市场。错误详情包含实际请求的交易所参数。缺少 Key 或接口失败时明确报错。Binance Stock 最新报价也共用此 Key。已有本机与服务端历史缓存继续按原缓存规则使用，缺失区间向 Twelve Data 查询。

新增标的、已有未使用标的首次用于记账／关注／启用定投，以及修改标的身份信息时，需要校验市场目录。已有交易、关注或启用定投的标的继续记账时复用已保存身份；单纯调整余额、记分红或买卖不重新比对实时目录名称，以免目录改名或暂时缺少名称阻止保存。实际修改名称、代码、市场等身份字段仍须校验。

A 股、境内 ETF、场外基金、港股通及国内期货期权使用东方财富查询，无需配置 API Key。搜索通过 `searchapi.eastmoney.com/api/suggest/get` 取得目录代码和名称，按资产类型、市场和币种筛选；保留去重、精确代码和名称／部分代码匹配。

A 股、境内 ETF、港股通和国内期货期权使用东方财富历史日线收盘价，显式请求不复权数据。核对返回代码与市场，剔除无效价格和区间外日期；当日日线在收盘前不作为历史收盘价。长序列按日期向前分页。国内期货期权映射各交易所市场编号和合约格式；东方财富缺少历史时，使用已配置的补充行情源查询，到期合约仍可能缺少数据，不能以零值补齐。

场外基金使用 `api.fund.eastmoney.com/f10/lsjz` 公布的历史单位净值，按日期范围分页，不使用盘中估值或累计净值替代单位净值。识别货币基金的每万份收益并明确提示不能将其作为净值。历史缺失或网络失败保留错误提示，不制造价格。

港股通使用港币报价、人民币结算，支持将 `700`、`00700` 规范为 `00700.HK`；当前搜索不校验港股通可交易名单。港股基金类别同时包含 REIT 时补查货币与行业元数据，防止将已有股票行业分类的 REIT 当作 ETF。

## 标的价格走势

股票、ETF、基金和加密货币现货详情保留持仓概况、买入、卖出及分红／余额调整入口，移除行情入口。资产走势通过三个下划线 Tab 切换价格走势、持仓数量／净投入变化和盈亏曲线，默认显示盈亏曲线。时间菜单位于卡片标题右侧，沿用资产趋势的紧凑文字与箭头样式，使用页面内自定义下拉菜单，支持建仓后、近 1 个月、3 个月、半年、1 年、2 年、5 年。

盈亏曲线按每日持仓估值减净成本、加已实现盈亏计算，包含买卖、费用、分红、送股及余额调整，以账户结算币种显示。更换时间范围只改变观察窗口，不清零累计盈亏；区间变化与区间前一天的累计值比较。当日缺价或缺港股通汇率时沿用此前最近一次有效数据；截至该日没有可沿用数据时才断开曲线，不以成交价补造行情。查询和计算只读，不修改账本或快照。

存款、大额存单、理财、保险、通用标的及合约详情同样提供盈亏曲线和卡片标题右侧的七档时间下拉。没有价格走势的标的通过两个下划线 Tab 切换原有金额／净投入／数量变化与盈亏曲线，默认显示盈亏。存款按实际记录余额及收支计算，支取利息计入累计盈亏，不按约定利率预估未到账利息；理财及保险使用截至所选日期已录入的估值。

交易记录统一为单条展开：点开一笔会收起其他明细；明细首行右侧的小字「修改」打开编辑页。保存只使用右上角勾号，底部提供「删除交易记录」及二次确认。保存后保留该笔明细，删除后更新持仓与盈亏并失效相关历史快照；不定位到曲线。加密现货调整记录显示调整前后数量和增减值，修改时填写调整后余额并按原流水在同日的顺序计算差额；允许增加与减少互换。现金分红、送股分别显示现金到账和持仓数量变化。

价格线使用未复权日线收盘价或基金单位净值，不以手动估值、盘中价或成交价补造日线。按标的报价币种显示；美股收盘价映射至对应北京时间日期。绿色圆点为当前账户的买入（含首次录入），红色圆点为卖出，位置使用流水中的日期和原始成交价。点击密集圆点可同时查看附近的多笔成交，拖动曲线查看历史价格。

历史查询中美股和美股 ETF 使用 Twelve Data，其他证券使用东方财富，期货期权可复用已配置的补充行情源；长区间按年分段，仅在内存中缓存，不写入账本、不执行定投或重算快照。无法取得的日期不补值，保留实际有数据的价格线并显示覆盖范围；部分查询失败时保留已取得数据并允许重试。

加密货币现货使用公开行情，无需配置密钥；仅使用 Binance 现货及日线，按用户确认的 1 USDT≈1 USD 估值；USDT 固定为 1，不查询额外换算源。价格按美元近似展示，日期按北京时间划分，只显示已完成的日线；通用余额标的不展示价格走势。

## 定投周期（0.5）

定投支持每日、每周固定星期、每两周固定星期、每月固定日期，不设置时分，日期按北京时间计算。首次执行日为创建日期之后的下一个匹配日期；每两周从首次计划日起每隔 14 天执行。每月可选 1 至 31 日，当月不足所选日期时按月末执行。

打开投资记账、前台刷新或执行快捷指令时，统一补记截至北京时间昨天的到期任务，今天的任务留到明天处理，流水仍使用对应的历史日期；不向券商或交易所下单。买入使用当期可用的历史报价，排除明确标记为未收盘的报价，缺少报价则等待，当期结束仍无报价则跳过；余额不足也跳过该期。同一任务、同一计划日期只记账一次。修改金额保留下次执行日，修改周期、目标或重新启用时重新安排下次执行日。

现有「同步 Hako 数据」快捷指令中的投资步骤名为「更新投资账本」，补齐截至北京时间昨天的历史日终快照，并保留历史定投流水。先读取服务端最新账本，仅在截至北京时间昨天的最近10个自然日内，补齐历史快照、到期定投标的以及新入金、新持仓估值需要的历史行情与汇率；同时按执行时刻补齐持仓和已到计划日期标的最近已收盘交易日的报价，A股按北京时间15:00、港股按16:00、美股按纽约时间16:00（自动处理夏令时），不再要求该行情所属的北京时间记账日已经结束，等待所有查询结束后，再按原有周期和资金规则补记截至昨天的定投买入、自动入金，最后基于新流水计算并保存快照；定投执行后不再查询行情或汇率。更早日期不补查，已有历史数据仍可用于估值和快照；手动完整重算不受该10日限制。快捷指令读取或重载账本时不另外启动不限日期的自动快照补数。尚未持仓的定投标的也参与补数，排除明确标记为未收盘的报价；当天任务留待日期结束后处理，不以昨日价冒充当日买入价。结果返回本次已记账、已跳过及等待报价的期数；估值不完整时明确报告失败，并保留已完成的定投结果。

收盘补数继续遵守10日查询下限，周末回到最近工作日，节假日及尚未发布的基金净值以数据源实际返回为准；不会生成虚构报价。正式收盘价可直接复用，盘中报价或收盘前查到的空结果不能阻止收盘后查询；沿用前值的估值也不能代替该交易日真实报价。仅提前补齐已收盘行情，不提前执行今天的定投或保存尚未结束的北京时间日终快照。

快捷指令的历史行情与汇率继续按本机缓存、服务端已有记录、行情接口的顺序补齐，仅请求历史快照缺失的数据；加密货币使用按北京时间划分、已结束日期的日终行情，不查询或复用当天现货报价来生成历史快照；当前定投买入仍仅支持股票、基金与 ETF，加密货币不新增定投买入功能。进入子应用和手动刷新仍可获取实时估值；定投统一采用计划日结束后次日补记的日期规则。

执行日志按实际流程分别计时记录；快捷指令显示读取服务端账本、补充历史行情与汇率、补记历史定投流水和保存每日快照，不包含当日报价缓存检查或现货查询。应用内实时刷新另外记录现货查询和定投结算。关键步骤分别计时记录当日缓存检查、行情与汇率准备、数据合并、定投记录生成、标的校验、快照影响范围、账本编码及差异比对、同步请求准备、服务器提交、确认数据解析与合并、账本解码、账户持仓汇总和本地缓存保存；账本无变化时明确显示无须提交服务器。行情准备复用现有可展开分组，显示标的行情、现货报价、加密历史行情和外币汇率四个并行分支，各分支耗时不能相加。应用内实时刷新最后单独检查并结算剩余定投。执行日志按标的记录行情、现货美元报价、历史行情和汇率查询，完成后显示有效报价数量、覆盖日期与来源。诊断信息另记每次实际 HTTP 请求（包括分页、重试和切换来源）的起止时间、耗时、请求时限、HTTP 状态或传输错误，不记录请求参数、正文或凭据。HTTP 成功仅表示收到响应，业务步骤通过解析与校验后才报告行情结果。每次实际请求完成都会推进后台进度；不使用定时器虚增进度。网络超时与系统取消分别记录，系统取消原因还包含整次后台运行时长，不能用当前步骤的耗时推断整次任务的可用时间。刷新流程按行情渠道分别调度独立标的，各渠道分别最多3个查询任务，不受其他渠道排队影响；现货、历史加密行情和汇率与标的查询同时启动，各自的依赖（如 USDT 换算报价）先准备；实际网络请求按最终访问的渠道执行上限（包括切换来源），同一标的的分页和补数窗口仍按顺序处理，USDT 换算报价先准备再用于依赖它的请求。子任务使用同一份账本输入，只返回报价和错误，汇总后一次更新账本；取消或账本版本变化时停止待执行任务，不发布过期结果。系统结束整次后台执行时停止后续工作；可在 App 中重试未完成任务。

接口使用 `frequency`（`daily` / `weekly` / `biweekly` / `monthly`）与 `schedule_day`：每日为 0，周周期为周一 1 至周日 7，月周期为 1 至 31。`next_date` 保存下次计划日期，也是每两周周期的基准。旧 `month_day` 格式不再接受。

定投周期结构从 schema 4 起使用 `frequency` 与 `schedule_day`。当前代码的数据库为 schema 9，启动时不再执行旧定投结构迁移；旧格式账本须先通过历史迁移版升级。

## 加密货币账户（0.4）

加密货币账户提供「现货」和「通用」两种标的，沿用现有账户卡片、持仓详情和原生表单布局。

- 现货按数量与行情估值；「调整余额」填写调整后的币数量，不填写美元市值。
- 通用标的只需名称，使用账户币种 USD，不依赖交易所目录、行情、保证金或定投。
- 首次录入填写投入金额，可选填当前余额；不填时余额等于投入金额。可以填写零余额。
- 后续「投入」「取出」同时改变账户现金、标的余额和净投入，不改变累计盈亏。
- 「调整余额」填写该日的实际余额，差额只改变盈亏，不记为投入或取出；允许调整到零，禁止负余额。
- 累计盈亏 = 当前余额 − 累计投入 + 累计取出。全部取出后保留历史盈亏，之后可以再次投入。

记账助手使用 `generic` 类型，以 `buy` / `sell` 记投入与取出（`price` 填金额，`quantity` 为 1）；`asset_balance` 记余额调整。首次投入可用 `settled_amount` 填实际余额。`crypto_contract` 和 `funding_balance` 已移除。

## 历史迁移与升级要求

当前代码使用投资 schema 9，其他数据库仍为 schema 2。服务端与 iOS 使用 0.9.x 兼容版本线，最低均为 0.9.0；Agent 1.5.10 的最低服务端要求也为 0.9.0。旧客户端的 UUID 标的引用及行情删除键不适用于新结构，需要配套更新。

schema 7/8→9 的临时迁移、启动调用和专项测试已清理。清理前通过 Agent 签名只读接口确认线上 schema 9、四张公共表的字段和主键、标的 ID 格式及持仓／关注／行情引用完整性，并确认没有迁移临时表。当前启动只初始化空库或打开 schema 9，不修改已有结构及数据。

历史迁移版提交 `9d8019d`（服务端 0.9.0）曾在同一事务中将投资 schema 7 或 8 升级为 9，以下仅记录历史行为：

- 汇率全局共享，删除 `book_id`，主键为 `rate_date + base_currency + quote_currency`。`source` 为普通字段，保留 `rate`、`available_at_utc`、`is_final` 和 `revision`。
- `market_instruments` 和 `market_derivative_specs` 全局共享，分别以 `id`、`instrument_id` 为主键。标的 ID 按“类型＋市场范围＋代码＋报价币种”生成，前缀全部大写，例如 `ETF:US:QQQM:USD`、`STOCK:HK:00700.HK:HKD`、`FUND:CN:017302.OF:CNY`、`CRYPTO:CRYPTO:BTC:USD`。同一美股在 IEX、纳斯达克等交易场所共用 ID；场外基金保留 `.OF`，A/C 等份额按各自代码分别识别。
- `market_daily_prices` 删除 `book_id`，主键改为 `instrument_id + session_date + price_type`，`source` 为普通字段。跨账本、跨来源的重复观察优先保留有效最终值，然后按实际收盘/发布时间、来源和原账本确定唯一记录，数值不重新舍入。临时行情可以升级为最终值，最终值不会被临时值降级。
- 私有 `investment_assets.id`、交易、手动估值和定投记录保留，资产及关注表的 `instrument_id` 重连至全局目录。`investment_assets.exchange` 保留原交易市场及港股通标识，避免改变结算方式；合约方向仍属于账本资产，合约乘数及到期信息属于全局合约规格。合并时遇到冲突的合约规格，迁移报错并整体回滚。
- 各账本的 generation、revision 增加一次，并标记历史快照重算。全部表结构、引用和版本变更在同一事务提交；失败回滚，重复启动不会再次迁移。

任何账本读取、导出以及新增持仓/关注时可复用同一份公共行情及汇率。账本全量上传只补充共享记录，未上传的日期保留；客户端删除私有持仓时不生成公共行情删除请求。明确的公共数据删除仍按全局记录处理，并校验所有账本的引用。共享价格或汇率变化时同步推进其他账本的 revision，并标记受影响快照失效；账户、交易和手动估值按原账本隔离。

代码不再包含投资 schema 3→4、4→5、5→6 和 6→7 的临时迁移，以及 7/8→9 的临时迁移，也不包含早期加密合约清理迁移。其他不支持的版本停止打开并保留原数据。

尚未升级的实例须先备份数据库，再按版本运行历史代码：

- schema 7 或 8：使用迁移版提交 `9d8019d`（服务端 0.9.0）成功启动一次，确认实际 schema 9、公共表结构及引用完整性，再部署当前代码。恢复旧版备份时也须按此步骤升级。
- schema 6：使用迁移版提交 `68f1e13`（服务端 0.8.2）成功启动一次，确认升至 schema 7 且数值精度已整理，再按 schema 7 的步骤升级；受影响的历史快照由 iOS 重算。
- schema 5：使用迁移版提交 `b8ff7b8`（服务端 0.8.0）成功启动一次，确认升至 schema 6 且月末表已移除，再按 schema 6 的步骤升级。
- schema 4：使用迁移版提交 `12ab8b6` 成功启动一次，升至 schema 5，再按 schema 5 的步骤升级。该迁移统一 `fund`／`wealth` 为 `fund_wealth`，保留账户及历史记录。
- schema 3：先运行 `12ab8b6`。迁移版只在没有旧定投及执行记录时升级定投结构，随后升级至 schema 5；有旧定投时停止且不修改数据，须先在旧版处理。
- schema 2：先运行 `7fd3ced`（服务端 0.4.0）完成加密合约清理，再按 schema 3 的步骤升级；不能从 schema 2 直接运行当前代码。

以下仅记录 `7fd3ced` 的历史行为，当前服务端不会执行：

历史迁移的清理范围仅限投资记账中的加密合约：

- 删除 `crypto_contract` 标的及其交易、资金费、保证金等流水、行情、关注、定投及执行记录；同步删除没有标的关联的旧 `derivative_funding` 流水。
- 删除 `investment_assets.collateral_asset_id`。
- 删除 `market_derivative_specs` 的 `pricing_model`、`settlement_basis`、`settlement_unit`。
- 删除 `investment_derivative_event_details` 的 `funding_target`、`settlement_to_account_rate`。
- 清除受影响账本的日、账户日和月统计快照，交由 iOS 按保留流水重算；增加所有账本的 generation / revision，拒绝迁移前的过期写入。

现有库没有仅用于加密合约的独立持久表。期货仍使用 `market_derivative_specs` 的乘数、到期日，以及 `investment_derivative_event_details` 的方向、交易动作、保证金字段，因此保留这些共用表。资产的 `settlement_unit` 同时用于其他资产结算，亦保留。独立的「加密资产」子应用不在本次清理范围内。

该清理不会把旧合约转换为通用标的，也不会生成补偿性现金流水。需要继续记录的通用标的由用户按实际投入和余额重新登记。

清理后的 schema 3 不支持旧版服务端回退读取。客户端接口和通用标的的记账逻辑不受临时迁移代码移除的影响。

账户管理拖动排序时立即更新本地显示顺序，保存期间显示加载状态并暂时禁止再次拖动，成功后使用服务端确认顺序；失败后恢复服务端已确认的列表并提示。隐藏归档账户时只调整可见账户在原槽位中的顺序，不移动隐藏账户，也不重算历史快照。

历史汇率补数先将周末起止日期归到上一个工作日，再排除纯周末缺口；缓存已有周五汇率时不发起周末查询，缺少时只补查工作日。估值延用此前最近的有效已发布汇率，不为周末创建虚构的汇率观察记录。工作日发布缺失时仍保留原有错误处理与最近有效值规则。

新增汇率固定使用欧洲央行（ECB）的公开日参考汇率，交叉计算外币兑人民币；不再使用 Twelve Data 补数。已有历史来源标签和有效汇率保留。ECB 返回的正式观察值标记 `is_final=1`；有效最终值在本地合并、磁盘缓存和服务端写入时均不被后续刷新覆盖。`is_final=0` 或未确认的前一工作日观察值会在进入子应用、快捷指令刷新时重新查询，即使历史估值快照已完整也要检查。已完成查询区间不能隐藏未确认值；查询失败不改变原有汇率和最终状态。当前日期还未发布时沿用此前已发布值，不伪造当前日期的汇率。


快捷指令执行详情支持复制全部子任务日志，子任务详情支持一键复制全量日志，原分享入口沿用相同的完整导出。导出包含应用版本、执行标识、触发来源、状态、起止时间、并行分支、阶段耗时汇总以及当前保留的全部原始事件和诊断详情，时间使用含毫秒的 UTC 格式。导出沿用脱敏规则，不额外截断详情；记录达到原有事件保留上限时注明较早事件可能已被移除，不声称能够恢复已淘汰的事件。

## 场外基金净值公布与重查

场外基金使用天天基金已公布的单位净值，保留实际净值日期及正式值标记；不使用盘中估算、不假设统一 T+1。收盘前查询截止上个工作日，收盘后可读取当日实际已公布净值。QDII 等尚未公布净值的日期作为待更新，不生成零值或复制旧净值记录。

iOS 自动刷新、快捷指令补数和详情历史查询共用净值缓存规则：已公布数据复用；尚未公布的查询尾段仅在进程内冷却 15 分钟，之后重查，重启后也不会被永久标记为空。前台每五分钟检查时，基金每十五分钟允许补查一次；成功但未公布的响应不记作行情失败。青龙从服务端领取历史净值任务，不领取场外基金当天最新价任务；新持仓／关注查询近三十天发现最近已公布净值。ETF 交易价格及其他市场规则不变。此次无需调整数据库结构。
